做作品集的时候我一直在想一个问题：**一个能拿去面试的项目，到底需要多复杂？**

写完之后我的答案是：不需要复杂，需要**完整**。能跑通"登录 → 写文章 → 前台看到 → 别人能访问"这条链路，比堆十个花哨的组件有用得多。

## 一、技术选型为什么这么选

- **Vue 3 + Vite**：启动快，单文件组件结构清晰，`<script setup>` 写起来接近写普通 JS。
- **Express**：最小可用，一个 `app.get()` 就是一个接口，理解成本低。
- **SQLite**：单文件数据库，不需要装 MySQL，`git clone` 之后直接能跑。

> 选型的第一原则不是"哪个更先进"，而是"我能不能一个人把它跑起来"。

## 二、踩过的坑

### 1. better-sqlite3 编译失败

第一次装依赖就卡住了，报错大意是缺少 C++ 编译工具链。Windows 上要装 Visual Studio Build Tools，几个 G。

后来发现 Node 22 以上内置了 `node:sqlite`，零依赖、零编译：

```js
import { DatabaseSync } from 'node:sqlite';
const db = new DatabaseSync('./data.db');
```

**教训**：遇到原生模块编译问题，先查查标准库有没有替代品。

### 2. Vite 只监听了 IPv6

服务起来了，但浏览器打不开 `127.0.0.1:5173`。原因是 Vite 默认绑到 `::1`。

```js
server: { host: true }
```

一行解决。

### 3. 跨域与代理

前端 5173、后端 3001，浏览器同源策略会拦。两种解法：后端开 CORS，或者用 Vite 代理把 `/api` 转发过去。

我两个都做了：开发用代理（前端代码里只写 `/api/posts`，不写域名），部署时同一个服务出静态文件和接口，天然同源。

## 三、数据表设计

只用了三张表：

| 表 | 作用 | 关键字段 |
|---|---|---|
| posts | 文章 | slug（唯一）、status、views |
| projects | 作品集 | sort_order |
| users | 管理员 | password（哈希） |

这里有个细节：**slug 必须唯一**，因为将来做 SEO 友好链接要用它。数据库层面加 `UNIQUE` 约束，比在代码里查一遍再插入可靠得多——并发下代码检查是有空隙的。
